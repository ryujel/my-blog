# 2048 게임 - Review 결과

테스트 환경: Claude_Browser 프리뷰 도구로 `2048-game/index.html`을 `file://` 경로로 직접 열어 조작. 데스크톱(기본 해상도)과 모바일 폭(375px) 두 가지 뷰포트에서 확인. 콘솔 에러는 세션 전체에서 0건.

테스트 방법론 참고: 임의 병합 상황(`[2,2,2,0]` 등)이나 2048 도달·완전 봉쇄 같은 상태는 정상 플레이만으로 재현하기 어렵기 때문에, 다음 두 가지 방법을 병행했다.
- (A) 실제 브라우저 조작: 방향키 입력(`ArrowUp/Down/Left/Right`)을 실제로 전송하고 렌더링된 DOM(`.tile` 요소들의 `grid-row/col`, 값, 점수)을 읽어 검증.
- (B) 화이트박스 유닛 테스트: `game.js`의 순수 함수(`slideRowLeft`, `canMove`, `boardHasValue`)를 원문 그대로 콘솔에 복사해 다양한 입력 배열로 직접 호출·검증 (실제 로직과 100% 동일한 코드, 상태만 격리).
필요한 경우 `Math.random`을 결정론적으로 오버라이드해 타일 스폰 위치/값을 통제한 뒤 실제 키 입력으로 재생하는 방식도 사용했다(예: 병합/점수 누적 확인).

## 체크리스트별 결과

### 1. 4방향 이동/병합 정확성 — Pass
실제 방향키 입력으로 확인:
- `ArrowDown`: (0,0)=2,(0,1)=2 → 두 타일이 각각 자기 열을 따라 (3,0),(3,1)로 이동 (병합 없음, 다른 열이라 정상).
- `ArrowRight`: row0의 단일 타일이 우측 끝으로 이동, row3의 [2,2]가 [0,0,0,4]로 병합(점수 +4).
- `ArrowRight` 재입력: [2,0,0,2] 형태가 압축 후 인접 판정되어 [0,0,0,4]로 병합(점수 +4, 누적 8) — gap이 있어도 압축 후 병합되는 표준 2048 규칙이 정확히 구현됨.
- `ArrowUp`: 열 압축/병합 정상 동작(점수 +8, 누적 16).
DOM에서 읽은 타일 좌표/값이 매 단계 수식으로 예측한 값과 정확히 일치.

### 2. 한 턴 1회 병합 규칙 (`[2,2,2,0]` → `[4,2,0,0]`) — Pass
`slideRowLeft` 원문 함수를 콘솔에서 직접 호출:
- `[2,2,2,0]` → `{row:[4,2,0,0], score:4, mergedIndices:[0]}` — 스펙 예시와 정확히 일치, `[4,4,0,0]`이 되지 않음.
- 추가 케이스도 모두 통과: `[2,2,4,4]`→`[4,8,0,0]`(score12), `[4,0,4,4]`→`[8,4,0,0]`(score8, 새로 생긴 8이 재병합되지 않음), `[2,2,2,2]`→`[4,4,0,0]`(score8, 두 쌍 모두 정상 병합), `[2,0,0,2]`→`[4,0,0,0]`(score4).

### 3. 변화 없는 이동 시 새 타일 미생성 — Pass
타일이 모두 상단 행에 정렬된 상태에서 `ArrowUp`을 연속 두 번 입력. 첫 번째는 정상 이동/병합, 두 번째는 보드에 변화가 없어 타일 개수(3개), 좌표, 점수(16)가 완전히 동일하게 유지됨 — `boardsEqual` 판정과 조기 `return`이 의도대로 동작.

### 4. 점수 누적 정확성 — Pass
연속 조작에서 점수가 0 → 4 → 8 → 16으로, 매 병합값만큼 정확히 누적됨을 확인 (항목 1 참고). BEST 값도 SCORE가 갱신될 때마다 동일하게 따라 올라가고, `localStorage`(`game-2048-best-score`)에도 즉시 반영됨을 확인.

### 5. 2048 도달 시 승리 표시 — Pass (제한적 검증)
실제 플레이로 2048 타일까지 도달시키는 것은 수십 회 이상의 정교한 병합이 필요해 이번 리뷰 범위에서 비현실적이라 판단, 다음 방식으로 검증:
- 원문 `boardHasValue(board, 2048)` 함수를 콘솔에서 직접 호출해 2048 이상 값이 있을 때 `true`, 없을 때 `false`를 정확히 반환함을 확인.
- `handleMove` 소스(game.js 251~256행)에서 `!hasWon && boardHasValue(board, WIN_VALUE)` 조건 충족 시 `hasWon=true`, `inputLocked=true`, `showOverlay('You Win!', true)`가 호출되는 것을 코드로 확인.
- 오버레이 DOM을 실제로 토글해(`overlay-message`="You Win!", `overlay-continue-btn` 표시) 화면에 "You Win!" 메시지 + "계속하기"/"새 게임" 버튼이 정상 렌더링됨을 스크린샷으로 확인.
- "계속하기" 버튼 클릭 시 오버레이가 정확히 닫히고(`overlay hidden` 클래스 확인) 이후 방향키 입력이 다시 정상 동작함을 확인.
자연 발생적인 2048 달성 시나리오 자체(hasWon 플래그가 실제 게임 진행으로 true가 되는 전 과정)는 검증하지 못했다는 점은 한계로 남긴다.

### 6. 더 이상 이동 불가 시 게임 오버 표시 — Pass (제한적 검증)
마찬가지로 완전 봉쇄 보드를 실제 플레이로 만들기 어려워 다음으로 검증:
- 원문 `canMove(b)` 함수를 체스판형 4x4 보드(인접 동일값 없음, 빈칸 없음)에 대해 호출 → `false` 정확히 반환. 인접값이 하나라도 같으면 `true`, 빈칸이 하나라도 있으면 `true` — 모두 스펙대로 동작.
- `handleMove` 소스(258~261행)에서 `!canMove(board)`일 때 `isGameOver=true`, `showOverlay('Game Over!', false)` 호출을 코드로 확인.
- 오버레이 DOM을 토글해 "Game Over!" 메시지 + "새 게임" 버튼만 표시(계속하기 버튼 숨김)되는 것을 스크린샷으로 확인.
- "새 게임" 버튼(오버레이 내부) 클릭 시 점수 0, 보드 초기화(2개 타일), 오버레이 숨김, BEST 값 유지를 확인.

### 7. "새 게임" 버튼으로 완전 초기화 — Pass
상단 "새 게임" 버튼과 오버레이 내부 "새 게임" 버튼 모두 테스트: 점수 0으로 리셋, 보드가 새 2개 타일로 재생성, `isGameOver`/오버레이 숨김 상태로 복귀. BEST 점수는 의도대로 유지됨(리셋 대상 아님).

### 8. 방향키 입력 시 페이지 스크롤 안 됨 — Pass
`game.js` 284~289행에서 매핑된 키(`ArrowUp/Down/Left/Right`)에 대해 `e.preventDefault()`를 호출하는 것을 코드로 확인. 실제 여러 차례 방향키 입력 후 `window.scrollY`/`scrollX`/`document.scrollingElement.scrollTop`을 확인한 결과 항상 0 유지.

### 9. 모바일 폭(375px)에서 레이아웃 확인 — Pass
뷰포트를 375x700으로 변경 후 스크린샷 확인: 제목/부제, SCORE·BEST 박스, 새 게임 버튼이 한 줄에 잘림 없이 배치되고, 보드는 정사각형을 유지하며 좌우 여백과 함께 잘리지 않고 표시됨. 텍스트/버튼 크기도 `clamp()`로 정상적으로 축소됨.

### 10. localStorage 최고점수 유지 확인 — Pass
BEST 점수를 16까지 올린 뒤 페이지를 완전히 새로고침(`navigate`)한 결과, BEST 박스에 16이 그대로 표시됨. `localStorage.getItem('game-2048-best-score')` 값도 "16"으로 유지됨을 확인.

### 11. `node build.js` 실행 시 기존 블로그 빌드 영향 없음 확인 — Pass
`node build.js` 실행 결과: `Built 4 post(s) into "docs/".` (에러 없이 정상 종료). 빌드 후 `docs/` 디렉터리에는 `assets/`, `index.html`, `posts/`, `search-index.json`만 존재하며 `2048-game` 관련 파일/폴더는 전혀 생성되지 않음을 확인. `build.js`는 `posts/`, `templates/`, `assets/{css,js,images}`만 읽고 `docs/`만 쓰기 때문에 `2048-game/` 폴더와 구조적으로 완전히 독립되어 있음(소스 코드 확인).

## 추가로 확인한 사항
- 콘솔 에러: 세션 전체에서 0건.
- 승리/게임오버 오버레이의 "계속하기"/"새 게임" 버튼 클릭 이벤트가 각각 올바른 핸들러(`resetGame`, 계속하기 시 `inputLocked=false` + `hideOverlay`)에 연결되어 있음을 확인.
- 터치 스와이프(`touchstart`/`touchend`)는 마우스 기반 자동화 도구로는 실제 터치 이벤트를 재현할 수 없어 직접 조작 검증은 하지 못했음. 다만 스와이프 핸들러는 키보드 입력과 동일한 `handleMove` 경로를 공유하므로 (game.js 291~315행) 로직적 위험은 낮다고 판단. 실제 모바일 기기에서의 스와이프 동작은 별도 확인을 권장.
- 테스트 중 자동화 도구에 `Down`/`Up`/`Left`/`Right`(방향 접두어 없는 키 이름)를 보냈을 때는 `keydown` 이벤트의 `e.key`가 빈 문자열로 들어와 게임이 반응하지 않았음 — 이는 자동화 도구의 키 이름 표기 문제였고, 실제 브라우저가 보내는 `ArrowDown` 등 정식 키 이름으로 재시도하니 정상 동작함. **게임 코드의 버그 아님** (실제 사용자의 방향키 입력은 항상 `ArrowUp/Down/Left/Right`로 들어오므로 영향 없음).
- 리뷰 중 `git status` 확인 결과 `CLAUDE.md`가 로컬에서 수정된 상태(untracked `2048-game/`, `specs/`도 함께 있음)였으나, 이는 이번 리뷰 세션에서 발생한 변경이 아니며 `2048-game/*`, `build.js` 등 지침에서 수정 금지한 파일들은 이번 리뷰 작업 중 전혀 건드리지 않았음.

## 발견된 버그
없음. 체크리스트 11개 항목 모두 스펙대로 동작을 확인했으며, 코드 상에서도 로직 결함을 발견하지 못했다.

## 종합 판정: **커밋 가능**

`2048-game/` 구현은 `spec.md`의 요구사항과 "테스트/검증 방법" 체크리스트를 모두 충족한다. 병합 알고리즘(한 턴 1회 병합, gap 압축 후 병합), 점수 누적, 무변화 이동 시 미생성, 새 게임 초기화, 방향키 스크롤 방지, 모바일 반응형, localStorage 최고점수 유지, 빌드 파이프라인 독립성이 모두 정상 동작한다. 승리/게임오버 조건은 실제 장시간 플레이 대신 원문 함수 유닛 테스트 + 오버레이 렌더링 확인으로 검증했다는 제한이 있으나, 로직 자체(코드 경로)는 명확하고 함수 단위 테스트 결과도 모두 기대값과 일치하므로 커밋을 막을 이유는 없다고 판단한다. 모바일 터치 스와이프는 자동화 한계로 미검증이니, 실제 기기에서 한 번 더 확인해보는 것을 권장한다(선택 사항, 커밋 차단 사유 아님).
